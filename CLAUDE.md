# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

The package manager is **bun** (`bun.lock`). Ignore CONTRIBUTING.md's yarn commands — it is stale (see "Stale docs" below).

```bash
bun run dev              # Next.js dev server on :3000
bun run build            # registry:fresh + next build — the registry is rebuilt on every prod build
bun run lint             # eslint
bun run registry:build   # regenerate __index__.tsx, registry.json, public/r/*.json
bun run registry:fresh   # registry:clean + registry:build (use after editing registry-*.ts)
bun run clean            # rm node_modules, .next, .source
```

There is no test suite. Verification is: `bun run lint`, then `bun run dev` and view the affected docs page.

> IMPORTANT: Always use Claude Fable model for research purposes & Always use Claude Opus 4.8 model for workflows/subagents.

## Architecture

EvilCharts is a **shadcn-style component registry** shipped as a Next.js docs site. Users don't install a
package — they run `shadcn add @evilcharts/<name>` and the source is copied into their project. That
copy-not-import model drives most of the design decisions below.

### The registry pipeline

Everything flows from `src/registry/`, and the generated artifacts are gitignored/rebuilt, never hand-edited:

```
src/registry/registry-{ui,chart,example,blocks}.ts   ← hand-written item definitions
        └─ src/registry/index.ts (concatenates all four into one Registry)
              └─ bun run registry:build
                    ├─ src/registry/__index__.tsx   ← GENERATED: name → React.lazy component map
                    ├─ registry.json                ← GENERATED: shadcn registry manifest
                    └─ public/r/*.json              ← GENERATED by `shadcn build`: per-item install payloads
```

Adding a chart/example/block requires **two** steps: create the `.tsx` under `src/registry/<kind>/`, then add
its entry to the matching `registry-*.ts`. A file with no registry entry is invisible to both the docs site and
the CLI. After editing any `registry-*.ts`, run `bun run registry:fresh` or `<ComponentPreview>` will render a
"not found in registry" message.

The four item kinds:

- **`ui/`** (`registry-ui.ts`) — shared primitives (`chart`, `tooltip`, `legend`, `dot`, `background`, `evil-brush`).
  Charts depend on these via `registryDependencies: ["@evilcharts/chart", ...]`, so installing a chart pulls them in.
- **`charts/`** (`registry-chart.ts`) — the 8 chart components users install. Target `components/evilcharts/charts/`.
- **`examples/`** (`registry-example.ts`) — `ex-*.tsx` files rendered by `<ComponentPreview name="ex-...">` in docs.
- **`blocks/`** (`registry-blocks.ts`) — `b-*.tsx` larger composed showcase blocks.

`src/components/evilcharts/{charts,ui}/` is empty and gitignored-in-spirit: it's the local install target so you
can test `shadcn add` against `http://localhost:3000/r/{name}.json` (see `registries` in `components.json`).

### Charts are compound components

All 8 charts (`src/registry/charts/*.tsx`) follow one pattern: a context-providing root plus subcomponents
exported from the **same file**, so the whole chart is a single installable unit.

```tsx
<EvilAreaChart data={data} config={chartConfig} xDataKey="month" stackType="stacked" showBrush>
  <Grid />
  <XAxis dataKey="month" />
  <Legend isClickable />
  <Tooltip />
  <Area dataKey="desktop" variant="gradient" isClickable>
    <Dot variant="border" />
    <ActiveDot variant="colored-border" />
  </Area>
</EvilAreaChart>
```

Conventions that follow from this and that new work must preserve:

- The root is `Evil<Type>Chart`; subcomponents use bare generic names (`Area`, `XAxis`, `Grid`, `Tooltip`,
  `Legend`). Names repeat across chart files by design — imports are per-chart, so `Area` from `area-chart`
  and `Bar` from `bar-chart` don't collide.
- Some subcomponents (`Dot`, `ActiveDot`, pie's `Label`) are **marker components that return `null`**. The root
  reads their props off `children` and configures Recharts itself; rendering them does nothing. Don't "fix"
  these into real renderers.
- Files are large (1000+ lines) on purpose — one file per chart is what gets copied into a user's project.
- Each chart exports a `useLoadingData` hook for skeleton/loading states.

### ChartConfig is theme-aware, not CSS-variable-based

This is the main deviation from upstream shadcn charts. Config takes explicit per-theme color arrays, not
`color: "hsl(var(--chart-1))"`:

```tsx
const chartConfig = {
  desktop: { label: "Desktop", colors: { light: ["#047857"], dark: ["#10b981"] } },
} satisfies ChartConfig;
```

`src/registry/ui/chart.tsx` validates at runtime that every `colors` object has at least one valid theme key
and throws otherwise. Arrays hold multiple stops for gradient variants.

### Docs are split by rendering-engine provider

`src/globals/constants/providers.ts` is the source of truth: `PROVIDERS`, `PROVIDER_META` (including an
`available` flag), and `providerFromPathname()`. Docs mirror the install-time provider choice:

```
/docs                              intro           (shared)
/docs/chart-config                 config contract (shared — identical across engines)
/docs/recharts                     provider landing
/docs/recharts/installation        provider-scoped
/docs/recharts/area-chart/static   provider-scoped
/docs/echarts/*                    placeholder; available: false
```

Recharts predates the split and was served from `/docs/<chart>`, so `next.config.ts` carries permanent
redirects from every legacy path. Those rules use an explicit chart-name alternation (`RECHARTS_CHARTS`) —
**never widen it to a bare `:chart` param**, or it will swallow `/docs/recharts` and `/docs/echarts`
themselves. Chart folders have no index page, so a separate rule sends `/docs/<provider>/<chart>` →
`.../static`. Adding a chart type means adding it to that alternation.

### Docs pipeline

Fumadocs MDX. `src/content/docs/**/*.mdx` → `source.config.ts` (frontmatter schema + `rehype-pretty-code`
with min-light/vesper themes) → generated `.source/` → `src/lib/source.ts` loader → `src/app/docs/[[...slug]]/page.tsx`.

MDX files don't import components — every component in `src/components/docs/mdx/index.tsx` is globally
available (`<ComponentPreview>`, `<ComponentSource>`, `<CliBlock>`, `<Steps>`, `<CodeTabs>`, `<ApiTable>`).
`<ComponentPreview name="x">` and `<ComponentSource name="x">` both resolve `name` through the generated
`__index__.tsx`, which is why registry entry + rebuild are prerequisites for docs to render.

Each chart's docs live at `src/content/docs/<provider>/<chart>/static.mdx` (bar-chart also has `blocks.mdx`),
with `meta.json` controlling sidebar order. Listing a page as `"ui/background"` in a `meta.json` `pages` array
flattens it to a page node rather than creating a `ui` folder — `NavMain` renders only folders, so that's what
keeps `ui/*` out of the chart list.

### Sidebar

Custom (shadcn `Sidebar` + `source.pageTree`), not Fumadocs' `DocsLayout` — so Fumadocs' `root: true` /
Layout Tabs behavior is unused, and provider filtering is done manually in `NavMain`.

**`DocsSidebar` must stay a server component.** `source` reaches into Fumadocs' server code, which imports
`fs/promises`; referencing it as a _value_ from a `"use client"` module pulls that into the browser bundle and
the build fails to resolve `fs`. Pathname-dependent logic lives in `sidebar-sections.tsx` (client), which
receives the tree as a serializable prop. `NavMain` gets away with `import { source }` only because it uses it
solely in a type position (`typeof source.pageTree`), which TypeScript erases — prefer the explicit
`Root` type from `fumadocs-core/page-tree` instead.

The Get Started / Chart Components / Documentation groups are hand-written lists in
`src/globals/constants/docs-sidebar.tsx`, not derived from content, so they're filtered against URLs that
actually exist in the page tree — otherwise a half-built provider renders links that 404.

`getNavItemIcon` keys off the **last segment** of a page-tree `$id` (`root:recharts/area-chart` → `area-chart`)
so one icon map serves every provider. It returns `null` for unknown ids, so a mismatch fails silently.

### Agent/LLM surfaces

The site serves itself to AI agents, and these routes are wired to real doc paths — adding a chart means
touching them:

- `src/proxy.ts` — Next.js 16 middleware (named `proxy`, not `middleware`). Rewrites `Accept: text/markdown`
  requests on `/docs/*` to `/llm/*`, and ingests `registry_install` + `docs_markdown_fetch` events to Axiom
  (`src/lib/axiom.ts`, no-ops without env credentials).
- `next.config.ts` rewrites — `/docs/<path>.md` → `/llm/<path>`. Depth is enumerated (1–3 segments) because
  the `.md` suffix binds to the final segment, which path-to-regexp can't express as a catch-all. A fourth
  level of nesting would need another rule.
- `src/app/mcp/route.ts` — static MCP server exposing `search_docs` / `read_doc`.
- `src/app/llms.txt`, `llms-full.txt`, `skill.md`, `.well-known/{agent-skills,skills}/` — agent-discovery endpoints.
- `src/lib/agent-docs.ts` — derives its page lists from `source.getPages()` and groups them by provider, so a
  new chart appears on its own. It publishes **only providers with `available: true`** — a placeholder provider
  is withheld so agents can't recommend components that don't exist. Flipping that flag in `PROVIDER_META`
  publishes a provider across llms.txt, llms-full.txt, and MCP at once.

## Conventions

- Path alias `@/*` → `src/*`. Prettier: 100 cols, double quotes, semicolons, with import-sort and
  tailwind-class-sort plugins — run Prettier rather than hand-ordering imports or classes.
- Tailwind v4 (CSS-first, no `tailwind.config`); theme lives in `src/app/globals.css`. shadcn style: new-york,
  base color neutral, RSC enabled.
- Registry components must be `"use client"` and import from `@/registry/...` (never `@/components/...`), since
  those paths are rewritten on install.
- Charts use `recharts` for rendering and `motion` for animation. Avoid new deps in registry components — each
  one becomes a required install for every user of that chart.
- File naming: kebab-case; examples `ex-*`, blocks `b-*`.
- Conventional commits (`feat:`, `fix:`, `docs:`, `chore:`).

## Stale docs

`CONTRIBUTING.md` predates a restructure and is wrong in ways that will misdirect you: it says yarn (it's bun),
`yarn gen-cli` (no such script — it's `bun run registry:build`), top-level `charts/`+`components/`+`scripts/`
(everything is under `src/`), `public/chart/` (it's `public/r/`), per-chart-type directories like
`charts/bar-charts/` (flat `src/registry/charts/`), and a `ChartConfig` using `color: "hsl(var(--chart-1))"`
(now `colors: { light: [...], dark: [...] }`). Trust `package.json` and the actual tree over that file.
